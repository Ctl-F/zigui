UI designer and event handlers (in the IDE)

In the IDE a .ui.zon file is both a text document and a visual design, and the Events tab connects each event to a function in your project: pick an existing handler, create a new one, jump to its source, and rename it later with its references updated.

Opening and creating UI documents

  • File > New UI Document... asks for a path (default ui/untitled.ui.zon), writes an empty document and opens it.
  • Double-click a .ui.zon file in Files, or use File > Design This Document on any open .zon tab.
  • The text opens as a normal editor tab; the builder's panels (Designer toolbar, Toolbox, Outline, Preview, Inspector) are docked beside it: the preview tabs with the text, the rest in a column on the right. They are ordinary dock panels, so rearrange or float them; View > UI Designer Panels brings them back, and closing the document's text tab hides them.

Two views, one file

Visual edits rewrite the text (one undo step in the text editor, and the tab shows the modified bullet); typing in the text re-reads the document whenever it parses. When it does not, the status line says why (ui/main.ui.zon: line 4:9: ...) and the design keeps its last good state. Save (Ctrl+S, the designer's Save button) saves the file. Undo in the design (Ctrl+Z with focus in a designer panel) and in the text are separate histories. Edit > Undo/Redo/Cut/Copy/Paste act on whatever has focus.

Events and handlers

A document stores an action name per event (.on = .{ .click = "okClick" }); the program turns names into calls. The IDE owns that mapping:

PieceWhat it is
Your handlersOrdinary methods you write and keep where you like: pub fn onOk(self: *App, ev: *zigui.event.Event) void in a struct, or fn (ev: *Event) void anywhere. Event may be spelled zigui.event.Event, zigui.Event or plain Event.
.zigide/actions.zonThe manifest: action name → struct, function and file, plus the default struct for new handlers. Keep it in version control.
ui_actions.zig (project root)Generated, do not edit. pub const Contexts has one pointer per struct that has bound methods, and register(actions, gpa, contexts) puts every action into a zigui.uiload.Actions.
// in your program
const ui_actions = @import("ui_actions.zig");
var actions: zigui.uiload.Actions = .{};
defer actions.deinit(gpa);
try ui_actions.register(&actions, gpa, .{ .app = &app });          // one field per struct, snake_case
const inst = try zigui.uiload.instantiate(&ui, parent, &doc, .{ .actions = &actions });

The Events tab

Select a widget, open the Events section of the inspector. Each event has a text field (type an action name by hand if you like) and two buttons:

  • ... lists the project's handlers grouped by file: one submenu per .zig file (src/main.zig > App.onSave, ...), so you drill down instead of scrolling one long list. The submenu holding the current handler is checked. Choosing one binds the event to it; if the function or its struct is not pub the IDE makes it so (the generated file imports it from another file), and the action is named after the function unless a binding already exists.
  • ... > New handler in ui/main.zig adds a stub method to the document's companion file and opens it at the new function. The companion is the Zig file with the same name next to the .ui.zon (ui/main.ui.zon → ui/main.zig, holding pub const Main = struct {...}; main_window.ui.zon → MainWindow). File > New UI Document creates it together with the .ui.zon; for an older document it is created the first time you add a handler (or the struct is added to the file if the file exists without it). New handler in... offers any struct in the project instead (including one that already has handlers). Without a document context the project's default struct is used (the one with the most handlers, remembered in the manifest), else a new ui_handlers.zig. The action is named from the widget's id and the event (okButton + click = okButtonClick, function onOkButtonClick; a number is added if the name is taken). If your file has no zigui import, one is added at the top.
  • ... > No handler clears the event (undoable). Go opens the bound handler's source.

Edits to a file that is open in an editor go into its buffer (so they are undoable there) and the file is saved so the disk, the manifest and ui_actions.zig agree; other files are rewritten on disk.

Renaming a handler

Put the caret on a handler's name and choose Refactor > Rename Event Handler... (F2). A bar asks for the new name; Enter shows what it would change (onReset -> onClear: 5 places in 2 files) and Enter again applies it. It changes the declaration, member accesses in its own file, and Struct.name in files that mention the struct, then updates the manifest and regenerates ui_actions.zig. The action name is unchanged, so UI documents need no edits. References are found by name, not by type: value.onReset(...) through a variable in another file is not touched (the preview count tells you how many it will change; review the diff). Moving a handler to another struct or file is planned. Refactor > Regenerate ui_actions.zig rewrites the generated file from the manifest.

The pieces (for tools)

  • ide.handlers (UI-free): scan (discover handlers and structs with std.zig.Ast), Manifest, generateBindings, planCreate, planBind, planRename (a list of FileEdits), and Handlers which applies plans through an optional open-buffer hook, updates the manifest and regenerates the binding file.
  • ide.designer.Designer: the document sync, the builder lifecycle and the HandlerProvider implementation.
  • ide.prompt.Prompt: the one-line question bar (ask(title, initial, hook), setTitle, keepOpen).
