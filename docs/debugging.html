Debugging

The IDE debugs your program through a debug adapter that speaks the Debug Adapter Protocol (DAP). It looks for lldb-dap first (also lldb-vscode, lldb-dap-NN, and the usual LLVM install folders) and falls back to gdb --interpreter=dap (gdb 14 or newer; best effort). If neither is found, the Debug console says what to install. Set debug.adapter_path in the settings to use a specific adapter.

Keys

KeyDoes
F5Start debugging (saves all, runs zig build, launches the program under the adapter); when stopped, continue
Ctrl+F5Run without debugging (save all and zig build run, the old F5)
Shift+F5Stop
F9Toggle a breakpoint on the cursor line (or click the gutter beside the line number)
F10 / F11 / Shift+F11Step over / step in / step out

All are commands (debug.start, debug.stop, debug.toggle_breakpoint, debug.step_over, debug.step_in, debug.step_out, view.debug) in the Debug menu and can be rebound.

The Debug panel

View > Debug (a tab beside Output) has a toolbar (Continue, Step Over, Step In, Step Out, Stop), the state, and: Call Stack (select a frame to see its locals and open its line), Breakpoints (double-click to open), Variables (Locals, Globals, Registers; children load when expanded and stay open across steps) and the Debug Console (the program's output, the adapter's messages and an expression box: type an expression and press Enter). The editor shows a red dot for a breakpoint (hollow = disabled, grey = not verified by the adapter, a different dot = conditional), a yellow arrow and a tinted line at the current line. Breakpoints follow their code when you edit the file above them.

Where things are kept

Breakpoints (and an optional run configuration) are saved in .zigide/debug.zon, with paths relative to the project:

.{
    .breakpoints = .{
        .{ .file = "src/main.zig", .line = 6 },
    },
    // optional; without it the IDE debugs the executable that `zig build` installed
    // .program = "zig-out/bin/app", .args = .{ "--flag" }, .cwd = ".", .stop_on_entry = false,
}

Without .program the IDE debugs the single executable in zig-out/bin.

Zig and variables

Stepping, breakpoints and call stacks work with any build. Locals do not with Zig's self-hosted x86_64 backend: lldb cannot read its DWARF variable locations, so the Locals scope is empty (the panel says so). Build the program with LLVM: in build.zig give the executable .use_llvm = true, or run zig build -fllvm.

Limits

  • Linux is the tested platform; macOS and Windows use the same code paths but are untested (on Windows use an lldb-dap or gdb build and set debug.adapter_path if it is not on PATH).
  • No conditional-breakpoint editor yet (the file format and adapter support exist), no watch list, no comptime debugging.
  • The adapter's requests to the client (run in terminal, ...) are answered with a failure, so the program's output appears in the Debug Console.

Comptime debugging (zigct, in progress)

Stepping through code while the compiler evaluates it. This needs zigct, a copy of the Zig 0.17.0 compiler with a debugger built in: tools/zigct/build.sh downloads the official source (checksum verified), patches it and builds it into ~/.cache/zigui-ide/zigct/0.17.0/bin/zigct (set ZIGUI_ZIGCT to use another). It only works for projects on exactly Zig 0.17.0. The IDE side (a “Debug comptime” command on a block, the panels showing it) is not wired yet; what exists is the compiler side, which speaks the same Debug Adapter Protocol as lldb-dap, so the call stack, locals and stepping map onto the panels above.

  • What a step is. A statement of the comptime code. Step In enters a call the compiler is evaluating at comptime, Step Over stays in the frame, Step Out runs until the frame ends; Continue runs to the next breakpoint, compile error or the end.
  • What you see. Frames: the comptime block, then each function being evaluated. Locals: every const/var in scope, with the current value (a comptime var changes as it is assigned). The compiler's own code in the standard library is skipped; only files under the project are stops.
  • Compile errors. With the compile_error exception breakpoint the session stops where the error is raised, with the stack still there, instead of after the compiler has unwound.
  • Running one block. A launch can name a target (file and line range): nothing stops until that block runs and the session ends when it finishes, so the rest of the build is not analyzed. The caller makes a small root file that imports the file (and references the function for a block inside one).
  • Limits. Function parameters are not listed yet; a repeated identical call is evaluated once by the compiler (memoized) so it is stepped once; a value is shown as one line of text (no expansion of structs yet); one session at a time; zigct keeps its own cache because its intermediate files carry extra debug markers.

Tests: zig build test replays scripts in test/ct/ against zigct and compares the stops with .golden files; they are skipped with a message when zigct is not built. Details for porting to another Zig version are in tools/zigct/README.md.

Code

ide.dap.client (framing, requests, events), ide.dap.session (state, frames, variables, breakpoints; tested with a fake adapter), ide.dap.adapters (discovery), ide.debugger.Debugger (spawns the adapter, owns debug.zon; poll every loop), ide.debug_marks (editor marks) and ide.DebugPanel. One end-to-end test runs a real lldb-dap when it is installed. Headless: cmd debug.toggle_breakpoint, cmd debug.start.
