Debugging

The IDE debugs your program through a debug adapter that speaks the Debug Adapter Protocol (DAP). It looks for lldb-dap first (also lldb-vscode, lldb-dap-NN, and the usual LLVM install folders) and falls back to gdb --interpreter=dap (gdb 14 or newer; best effort). If neither is found, the Debug console says what to install. Set debug.adapter_path in the settings to use a specific adapter.

Keys

KeyDoes
F5Start debugging (saves all, runs zig build, launches the program under the adapter); when stopped, continue
Ctrl+F5Run without debugging (save all and zig build run, the old F5)
Shift+F5Stop
F9Toggle a breakpoint on the cursor line (or click the gutter beside the line number)
F10 / F11 / Shift+F11Step over / step in / step out

All are commands (debug.start, debug.stop, debug.toggle_breakpoint, debug.step_over, debug.step_in, debug.step_out, view.debug) in the Debug menu and can be rebound.

The Debug panel

View > Debug (a tab beside Output) has a toolbar (Continue, Step Over, Step In, Step Out, Stop), the state, and: Call Stack (select a frame to see its locals and open its line), Breakpoints (double-click to open), Variables (Locals, Globals, Registers; children load when expanded and stay open across steps) and the Debug Console (the program's output, the adapter's messages and an expression box: type an expression and press Enter). The editor shows a red dot for a breakpoint (hollow = disabled, grey = not verified by the adapter, a different dot = conditional), a yellow arrow and a tinted line at the current line. Breakpoints follow their code when you edit the file above them.

Where things are kept

Breakpoints (and an optional run configuration) are saved in .zigide/debug.zon, with paths relative to the project:

.{
    .breakpoints = .{
        .{ .file = "src/main.zig", .line = 6 },
    },
    // optional; without it the IDE debugs the executable that `zig build` installed
    // .program = "zig-out/bin/app", .args = .{ "--flag" }, .cwd = ".", .stop_on_entry = false,
}

Without .program the IDE debugs the single executable in zig-out/bin.

Zig and variables

Stepping, breakpoints and call stacks work with any build. Locals do not with Zig's self-hosted x86_64 backend: lldb cannot read its DWARF variable locations, so the Locals scope is empty (the panel says so). Build the program with LLVM: in build.zig give the executable .use_llvm = true, or run zig build -fllvm.

Limits

  • Linux is the tested platform; macOS and Windows use the same code paths but are untested (on Windows use an lldb-dap or gdb build and set debug.adapter_path if it is not on PATH).
  • No conditional-breakpoint editor yet (the file format and adapter support exist), no watch list, no comptime debugging.
  • The adapter's requests to the client (run in terminal, ...) are answered with a failure, so the program's output appears in the Debug Console.

Comptime debugging

Stepping through code while the compiler evaluates it. Put the cursor inside a comptime { ... } block (or a comptime expression) and press Ctrl+F7 (Debug > Debug Comptime Block at Cursor). The Debug panel's status says Compile-time debug (zigct) so it is never taken for a runtime session. The session stops at the first statement of the block; then the usual keys work: F10 next statement, F11 step into a function the compiler is evaluating, Shift+F11 run until the current function ends, F5 continue to the next breakpoint, Shift+F5 stop. Breakpoints (F9 or the gutter) are shared with runtime debugging. When the block has been evaluated the session ends; the rest of the project is not analyzed.

  • What you see. Call stack: the block (named after its function, or comptime), then each function being evaluated at comptime. Variables: every const/var in scope with its current value; a comptime var changes as it is assigned. Values open: structs and tuples into fields, arrays and slices into elements (the first 200), optionals into their payload, unions into the active field, pointers into what they point to, and a type value into its fields and their types. A second scope, Compiler, shows the backward-branch count against the quota (the @setEvalBranchQuota limit, 1000 by default) so you can see a loop approach “evaluation exceeded N backwards branches”. The compiler's code in the standard library is skipped: only the project's files are stops.
  • Compile errors and @compileLog. The session stops where an error is raised, with the stack and locals still there (Debug > Comptime: Stop at Compile Errors toggles this; on by default). Every @compileLog is also printed in the Debug console as it happens; Comptime: Stop at @compileLog makes it a stop.
  • Watching types being built. The Types panel (View > Types Panel, a tab beside Debug) lists the struct, union, enum and opaque types the compiler creates while your code runs, newest first: declared (the type exists), layout resolved (fields and size are known) and fully resolved (default values too). A generic such as Pair(u32, Color) appears when your code first asks for it, so stepping over const P = Pair(u32, Color); shows it arrive. Select a type while stopped to see its size, alignment and fields; double-click opens its declaration; the filter matches name or kind. Only types requested while something of the project is on the stack are listed (so the standard library's own types appear when your code needs them, not before).
  • Needs. Zig 0.17.0 exactly (see Zig versions) and zigct, a copy of that compiler with a debugger built in. Zig > Build Comptime Debugger (zigct) writes out the build script, downloads the official source (sha256 checked), patches it and builds it into ~/.cache/zigui-ide/zigct/0.17.0/bin/zigct, with progress in the Output panel (a few minutes; nothing is installed elsewhere). ZIGUI_ZIGCT names another binary. Without it the command says what to do.
  • How the block is run. The IDE saves all files and, when the project has a build.zig, asks the build for its module graph: it runs zigct build --verbose in a dry-run mode where the compile steps do nothing, so the build prints the exact compile command of each artifact (modules, @import("name") mappings, packages from build.zig.zon, target, optimize mode) without building anything. (The status line says reading the build; the first time it also compiles the build script, which can take a minute, later runs reuse ~/.cache/zigui-ide/zigct/graph-cache.) It then finds the module whose folder holds the file with the block, writes two tiny files, .zigct-target.zig (in that module's folder; it imports your file and takes the address of the function the block is in) and .zigct-root.zig (in the artifact's root module folder; it imports the first), and evaluates the artifact with its root replaced by the second. Both files are deleted when the session ends. So the block sees exactly the imports and dependencies the real build gives it. Blocks inside a dependency from the package cache are not supported (the IDE will not write into it); path dependencies are. Without a build.zig, or when no module of the build holds the file, the file is evaluated alone with the project folder as its module (the console says so) and packages are not available. A block in a function needs the function to be pub and without comptime/anytype parameters (their arguments are unknown); the status line says so otherwise. A block inside a test declaration runs the compiler like zig test; that needs the file to belong to the artifact's own module, not to a dependency. Only the comptime parts of a test are evaluated by the compiler: the test's ordinary statements run when you run the tests, not here.
  • Limits. A repeated identical call is evaluated once by the compiler (memoized), so it is stepped once; types made with the reify builtins (@Type and friends) are not reported yet; a union type's fields are listed but not its enum tag values; one session at a time; zigct keeps its own cache (~/.cache/zigui-ide/zigct/cache) because its intermediate files carry extra debug markers.

The compiler side (zigct dap-comptime) speaks the same Debug Adapter Protocol as lldb-dap, so the panels are shared; its launch arguments are described in src/ide/dap/zigct.zig and the patch in tools/zigct/README.md. zig build test replays scripts in test/ct/ against zigct and an end-to-end test drives the IDE's Debugger with it; they are skipped with a message when zigct is not built.
