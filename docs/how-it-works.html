How it works

The tree

Everything on screen is a node in one tree owned by the Ui (ui.tree, root ui.tree.root). A node has a style (how it is sized and arranged), a visual (background, border, corner radius), a rectangle computed by layout, listeners, and optionally text and a widget.

A widget is behavior attached to a node: a Button keeps hover/pressed state and turns clicks into callbacks; a TextField keeps text and a caret. Widgets are created with ui.add(Widget, parent, options). Plain containers are bare nodes:

const panel = try ui.tree.create(.{
    .style = .{ .direction = .column, .gap = .px(6), .padding = zigui.style.Edges.all(8) },
    .visual = .{ .background = zigui.Color.rgb(34, 36, 41), .radius = 4 },
});
try ui.tree.appendChild(parent, panel);

Handles, not pointers

Nodes and widgets are referred to by Handle (an index plus a generation). A handle to something that has been destroyed simply stops resolving: ui.tree.get(h) returns null. Widget pointers returned by ui.add stay valid until that widget is destroyed (pool chunks never move). Destroy a whole subtree with ui.tree.destroySubtree(h); destruction requested during event dispatch is deferred until dispatch finishes.

Props, out, and setters

Each widget has:

  • props: the state you control (text, enabled, variant, colors...). Prefer the setters (button.setText("x"), button.setEnabled(false)): they mark the right dirty category. Writing a prop field directly is allowed in Zig; in Debug and ReleaseSafe builds a shadow checker warns when you changed something without telling the toolkit.
  • out: what the toolkit reports back each frame (clicked, hovered, changed, caret...). Per-frame flags are cleared by ui.endFrame().

You can react to widgets two ways: register a callback in the options (.on_click, .on_change) or read out after ui.update().

The frame

  1. Input calls (ui.pointerMove, ui.key, ...) dispatch events immediately and mark nodes dirty.
  2. ui.update() lets widgets refresh derived state (shape text, compute out).
  3. ui.renderFrame() runs layout (measure bottom-up, place top-down), then paint into a fixed-capacity DrawList, then submits to the backend. Only the damaged rectangle is repainted and presented.
  4. ui.endFrame() clears per-frame state.

Dirtiness is tracked per category (layout, paint, text, children...). A change that cannot affect layout (a color) repaints without relayout. Nodes flagged relayout_boundary stop layout dirtiness from climbing past them; repaint_boundary nodes cache their painted subtree.

There is no allocation on the frame path: the draw list storage is allocated once at startup. If you see a "draw list full" error, give DrawList.init bigger buffers.

Ownership

  • Strings you pass to widgets (.text = "...", setText, placeholders) are copied; the toolkit owns the copy and frees it. You may free yours immediately.
  • Exception: CodeEditor's Options.text is borrowed; use loadText(bytes, true) to hand over an allocation. See CodeEditor.
  • The Ui must not move after widgets exist (see Getting started).
  • The UI core is single-threaded. Call into it from one thread only; to wake a sleeping loop from another thread use the platform's wake().

Accessibility basics

Nodes have a role and a label. Built-in widgets set them. For your own interactive node use ui.makeClickable(h, .{ .label = "Open", .on_click = ... }), which makes it focusable, Tab-reachable, activated by click/Enter/Space, and gives it a pointer cursor. In Debug and ReleaseSafe the toolkit warns (ui_check:) about interactive nodes without a label; set one with ui.tree.setLabel(h, "name").
