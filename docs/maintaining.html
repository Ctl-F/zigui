Maintaining these docs

These pages are a living document. The rule: a feature or widget is not done until it is documented. The same change that adds it updates the docs.

Checklist

  • New widget: add docs/widgets/NAME.html (copy an existing page: description, example, Options table, Out table, Methods, Document form), add it to the table in docs/widgets/index.html, add one line to docs/nav.js, and add it to the lists on docs/index.html and docs/documents.html.
  • Widget-specific context-menu commands: a widget may declare pub const actions = [_]common.Action{ .{ .label = "...", .toggle = "bool_prop" } }; the builder shows them in the right-click submenu. List them on the widget's page.
  • New layout mode or style field: update layout.html (and the builder's Layout section in builder.html if it can edit it).
  • New event, command, or shortcut behavior: events.html.
  • New theme field or painter: theming.html.
  • Changed or removed API: fix every snippet that used it. Search the docs for the old name.
  • New builder feature, shortcut, or example program: builder.html / testing.html.
  • IDE-level code (under src/ide/): document it on ide.html. The framework must never import it.
  • New page: add it to nav.js and link it from index.html.

Style

  • Static HTML, no build step; style.css and nav.js are shared. Pages open from disk (file://) as well as from a server. Pages in docs/widgets/ set data-root="../".
  • Show a small example first, then the reference tables. Use the exact names from the source; if a snippet is not copied from a compiling example, double-check it against the code.
  • State limits plainly ("not yet: ...") so readers do not hunt for features that do not exist.
